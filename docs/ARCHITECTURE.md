# 아키텍처 & 기술 스택

## 1. 전달 방식 결정: 방식 3 (웹 + PDF), 단 "단일 소스" 구조

세 가지 전달 방식을 비교한 결과는 다음과 같습니다.

| 방식 | 장점 | 단점 | 결론 |
|------|------|------|------|
| 1. PDF 다운로드 | 구현 쉬움, 소장 욕구 | 수정·공유·재방문 불가, 확장성 낮음 | 단독으로는 ❌ |
| 2. 웹 리포트 | 수정·공유·재방문·추가상품 용이 | "소장"·"선물" 감성 약함 | 좋지만 부족 |
| 3. 웹 + PDF 동시 | 두 방식의 장점 결합, 상품성 최고 | 잘못 만들면 디자인을 2번 작업 | ✅ 채택 |

### 함정과 해법

방식 3의 흔한 실패는 **"웹용 화면"과 "PDF용 화면"을 따로 만드는 것**입니다.
유지보수 비용이 2배가 되고 디자인이 어긋납니다.

해법은 **분석 데이터를 단일 소스(JSON)** 로 두고, **리포트 UI 컴포넌트를 한 벌만** 만든 뒤
같은 컴포넌트를 두 출력 채널로 보내는 것입니다.

```
                ┌──────────────────────────────┐
   입력         │  사주 분석 파이프라인          │
 이름/생년월일  │  만세력 계산 → 오행/십성 →     │
 /성별/시간 ──▶ │  LLM 해석 → ReportData(JSON)  │
                └──────────────┬───────────────┘
                               │  (Single Source of Truth)
                ┌──────────────┴───────────────┐
                ▼                               ▼
        ┌───────────────┐               ┌───────────────┐
        │  웹 리포트     │               │  PDF 생성      │
        │  Next.js SSR  │  같은 컴포넌트 │  Playwright →  │
        │  /report/:id  │ ────────────▶ │  /report/:id   │
        │               │   재사용       │  를 print 렌더 │
        └───────────────┘               └───────────────┘
```

PDF는 별도 템플릿이 아니라 **웹 리포트 페이지에 `?print=1`로 접속해 인쇄 CSS를 적용한 결과**를
헤드리스 브라우저로 캡처합니다. 디자인 소스는 영원히 하나입니다.

## 2. 기술 스택 추천: All-TypeScript (Next.js + Playwright)

사용자 질문("아직 미정 / 추천해줘")에 대한 답입니다. 두 후보를 비교합니다.

### 후보 A — All-TypeScript (Next.js + Playwright) ✅ 추천

| 영역 | 선택 |
|------|------|
| 프론트/SSR | Next.js (App Router) + React + TypeScript |
| 스타일 | Tailwind CSS (인쇄용 `print:` 변형 내장) |
| 사주 계산 | TS 만세력 모듈(자체 구현 or `lunar-javascript`/`manseryeok` 류) |
| LLM 해석 | Claude API (`@anthropic-ai/sdk`) |
| PDF 변환 | Playwright(Chromium) 헤드리스 → `page.pdf()` |
| 데이터 | PostgreSQL(리포트 영속) + 객체 스토리지(PDF 캐시) |
| 배포 | Vercel(웹) + 별도 워커(PDF 렌더) 또는 단일 Node 서버 |

**장점**
- 웹 컴포넌트를 **그대로** PDF로 굽기 때문에 단일 소스 구조가 자연스럽다.
- 언어가 하나(TS) → 데이터 모델(ReportData 타입)을 분석·웹·PDF가 공유.
- Playwright `page.pdf()`는 실제 Chromium 렌더라 CSS 재현도가 가장 높다(그래프·웹폰트·그림자까지).
- 배포·인력·생태계가 단순.

**단점/유의점**
- 만세력(절기·진태양시·서머타임) 계산을 JS로 검증해야 함 → 계산 모듈을 격리하고 테스트로 고정.
- Playwright는 메모리를 먹으므로 PDF 생성은 **큐 + 워커**로 분리 권장.

### 후보 B — Python 백엔드 + 웹 프론트 분리

| 영역 | 선택 |
|------|------|
| 분석 | Python(FastAPI) + 만세력 라이브러리 + WeasyPrint |
| 프론트 | Next.js 별도 |
| PDF | WeasyPrint(HTML/CSS → PDF, 헤드리스 브라우저 불필요) |

**장점**
- Python 사주/천문 라이브러리 생태계가 풍부(절기·진태양시 계산 정확도).
- WeasyPrint는 브라우저 없이 가벼움(메모리 적음).

**단점**
- 웹 리포트(React)와 PDF(WeasyPrint)가 **다른 렌더 엔진** → CSS 재현 차이로 결국 디자인 2벌 위험.
- 언어가 둘로 나뉘어 데이터 모델·타입을 양쪽에서 중복 정의.
- WeasyPrint는 최신 CSS(grid 일부, JS 차트) 미지원 → 오행 그래프 등은 SVG 사전 렌더 필요.

### 결론

> **후보 A (All-TypeScript) 채택.**
> "웹과 PDF의 디자인을 절대 두 번 만들지 않는다"는 핵심 원칙을 가장 잘 지키는 구조이기 때문.
> 만세력 계산의 정확도 우려는 **계산 로직을 독립 모듈 + 스냅샷 테스트**로 격리해 해소한다.
> 정 안 되면 그 모듈만 Python 마이크로서비스로 떼어낼 수 있게 인터페이스를 좁게 유지한다.

## 3. 시스템 구성(서비스 플로우)

```
결제 ─▶ 분석 작업 큐 ─▶ ReportData 생성 ─▶ DB 저장
                                              │
                          ┌───────────────────┼───────────────────┐
                          ▼                                       ▼
              report.myfortune.ai/:id              (백그라운드) PDF 워커
              (웹 리포트 즉시 열람)                  Playwright로 :id?print=1
                                                    렌더 → 스토리지 업로드
                                                              │
                                                              ▼
                                          download.myfortune.ai/:id.pdf
```

- **웹 리포트는 즉시** 제공(분석 완료 시점).
- **PDF는 비동기**로 굽고 완료되면 다운로드 링크 활성화 → 사용자 체감 대기 0.

## 4. URL/라우팅 설계(초안)

| 경로 | 용도 |
|------|------|
| `POST /api/reports` | 입력(이름·생년월일·성별·출생시각) 받아 분석 작업 생성, `reportId` 반환 |
| `GET /report/:id` | 웹 리포트(SSR). 상단 캐릭터 카드 → 스크롤 섹션 |
| `GET /report/:id?print=1` | 인쇄 전용 레이아웃(PDF 워커가 접근) |
| `GET /api/reports/:id/pdf` | PDF 생성 상태/다운로드 URL |
| `GET /api/reports/:id` | ReportData(JSON) — 디버그/재렌더용 |

`:id`는 추측 불가능한 짧은 토큰(예: `8F4D2A`, nanoid)으로 발급해 링크 공유 가능 + 비공개성 확보.

## 5. 보안/프라이버시 메모

- 생년월일·출생시각은 민감 개인정보 → 저장 시 최소 수집, 리포트 토큰으로만 접근.
- 공유 링크는 토큰 기반이지만 "검색 불가" 수준. 진짜 비공개가 필요하면 만료/비번 옵션 추가.
- LLM에 보내는 프롬프트에는 식별 최소화(이름은 호칭용으로만, 필요 시 가명 처리 옵션).
